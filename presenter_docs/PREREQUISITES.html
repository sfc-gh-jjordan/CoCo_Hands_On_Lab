CoCo Interactive Workshop

Prerequisites

Everything you need in place before the session, so the first lab starts on time. Budget about 20 minutes. Works on macOS and Windows.

Do step 2 first, and do it early. Enabling cross-region inference needs an account administrator and is the single most common reason CoCo does not work on the day. Everything else you can do yourself in a few minutes.

What you are setting up

  • 1
    A Snowflake account you can create a database in You, or your admin
  • 2
    Cross-region inference enabled admin ACCOUNTADMIN only -- CoCo will not run without it
  • 3
    At least one CoCo surface Snowsight needs nothing installed and covers most labs. Desktop for the three that write files
  • 4

  • 5
    A named connection, tested So snow sql -c <name> just works
  • 6

Short on time? Steps 1, 2 and 6 are the ones that matter. With those done you can run several labs entirely in the browser using CoCo in Snowsight, with nothing installed at all.

1. Snowflake account access

You need an account and a role that can create a database. Each lab builds its own database named COCO_HOL_LABnn_DB and drops it again afterwards.

Use a non-production account. The labs create real account-level objects: one database per lab with sample schemas and seeded tables, a warehouse, and — depending on which labs you run — dynamic tables that refresh on a schedule, data metric functions that bill serverless credits until removed, and masking policies. Everything is namespaced with your user name and every lab has a teardown script, so nothing is shared and nothing is permanent, but a sandbox, dev or trial account is the right place to do this. So is the freedom to get things wrong.

If your organisation prefers a purpose-built role over ACCOUNTADMIN, admin_setup/01_coco_hol_setup.sql creates one called COCO_HOL_USER with exactly what the core labs need, and prints the GRANT ROLE statement to run for each attendee. You do not need ACCOUNTADMIN for any lab.

If none of your accounts are a good fit, ask your Snowflake team before you work around it. Two situations come up often: your non-production account inherits production's role model, so CREATE DATABASE and the governance privileges are not available to you; or your organisation would rather attendees did not hold elevated privileges in any account it owns. In either case your Snowflake sales engineer can provision temporary trial accounts for the session, in which you are the administrator and everything you build is disposable. It needs about a week's notice, so raise it as early as you can rather than on the day.

2. Enable cross-region inference admin

This is the step that blocks people. CoCo and several Cortex features require cross-region inference, and the controlling parameter is DISABLED by default in most existing accounts. If it is off, CoCo simply cannot be used -- there is no workaround at the user level.

Check the current setting

Anyone can run this in a Snowsight worksheet:

SHOW PARAMETERS LIKE 'CORTEX_ENABLED_CROSS_REGION' IN ACCOUNT;

Read the value column:

ValueWhat it means
ANY_REGIONBroadest access and highest capacity. Nothing more to do.
AHOL_US, AHOL_EU, AZURE_US, AZURE_EU, GCP_US … Restricted to a cloud and geography. Fine for the workshop, as long as it is not DISABLED.
AHOL_GLOBAL, AZURE_GLOBAL, GCP_GLOBAL Restricted to one cloud provider, any geography. Also fine.
DISABLEDCoCo will not work. This needs changing before the session.

Enable it

An ACCOUNTADMIN must run one of these. It can only be set at the account level -- not per user, not per session, and not by ORGADMIN.

-- Broadest model access and capacity (recommended for the workshop)
ALTER ACCOUNT SET CORTEX_ENABLED_CROSS_REGION = 'ANY_REGION';

-- Or keep inference inside one cloud provider
ALTER ACCOUNT SET CORTEX_ENABLED_CROSS_REGION = 'AHOL_GLOBAL';

-- Or keep it inside one cloud and geography
ALTER ACCOUNT SET CORTEX_ENABLED_CROSS_REGION = 'AHOL_EU';

What to tell your security team. Your stored data never leaves your account's region. During inference the prompt and the response transit to the processing region for the duration of the request and are not persisted there. Traffic within one cloud provider stays on that provider's private backbone; across providers it uses mutually authenticated TLS. Credits are billed in your own region, and there are no data egress charges.

Some newer accounts already have this on: for organisations created in commercial regions after 9 March 2026, ANY_REGION is the default, and a 2026_06 behaviour change sets a same-cloud default for many existing commercial accounts. Check rather than assume. Details: Cross-region inference.

While you have an admin's attention

Two other account-level things are worth confirming in the same conversation:

  • Cortex access. The SNOWFLAKE.CORTEX_USER database role is granted to PUBLIC by default. If your organisation revoked it, it needs granting back to your role.
  • Per-surface credit limits. A user needs a non-zero daily limit as well as the role. A value of 0 blocks that surface entirely: CORTEX_CODE_{CLI|DESKTOP|SNOWSIGHT}_DAILY_EST_CREDIT_LIMIT_PER_USER. The default, -1, means no limit.

3. Install a CoCo surface

You need at least one. Snowsight needs nothing installed -- if you are short on time or cannot install software, that alone is the recommended surface for most of the labs. Install Desktop if you want the two that write files to your machine (labs 04 and 08); it can also stand in for every other lab except 13, which is specifically about CoCo inside your own IDE. The CoCo CLI is optional -- lab 11 is the only lab that can use it, and Desktop's built-in terminal does the same job.

CoCo Desktop

  1. Download the build for your chip from the CoCo product page -- Apple silicon and Intel are separate downloads.
  2. Open the .dmg and drag the app to Applications.
  3. Launch it and sign in to Snowflake when prompted.

CoCo CLI

curl -LsS https://ai.snowflake.com/static/cc-scripts/install.sh | sh

Then check it:

cortex --version

If cortex is not found, the installer put it in ~/.local/bin, which may not be on your PATH. Either use the full path ~/.local/bin/cortex, or add it:

echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc

CoCo Desktop

  1. Download the installer from the CoCo product page. There are separate builds for Intel/AMD and ARM (Surface and similar), and each has a User installer (no admin rights needed) and a System installer (all users). Pick User unless your IT policy says otherwise.
  2. Run the .exe and follow the prompts.
  3. Launch it and sign in to Snowflake when prompted.

CoCo CLI

In PowerShell:

irm https://ai.snowflake.com/static/cc-scripts/install.ps1 | iex

Then close and reopen PowerShell so the PATH change takes effect, and check it:

cortex --version

If the script is blocked by execution policy, run PowerShell as your own user and allow the current process only:

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

That lasts for the current window only and does not change machine policy.

CoCo in Snowsight -- nothing to install

Sign in at app.snowflake.com. CoCo appears inside Snowsight across Workspaces and Notebooks. This is the fastest way to confirm your account is set up correctly: if CoCo responds in Snowsight, steps 1 and 2 are done.

4. Install the Snowflake CLI (snow)

This is a different tool from the CoCo CLI. snow runs SQL; cortex is the agent. Every lab uses snow to run its setup and teardown scripts.

Homebrew is the simplest route:

brew install snowflake-cli

That community formula updates automatically but can lag a release. For the Snowflake-maintained build instead:

brew tap snowflakedb/snowflake-cli
brew trust --cask snowflakedb/snowflake-cli/snowflake-cli
brew install --cask snowflake-cli

No Homebrew? Download the macOS package installer from the installation docs, or install it as a Python tool (needs Python 3.10+):

uv tool install snowflake-cli
# or
pipx install snowflake-cli

The Windows installer is the simplest route. Download it from the installation docs, run it, then open a new terminal so the PATH change takes effect.

Or install it as a Python tool (needs Python 3.10+):

uv tool install snowflake-cli
# or
pipx install snowflake-cli

Works in PowerShell, Windows Terminal or Command Prompt. The lab commands are identical on Windows -- only the shell prompt differs.

Confirm it works:

snow --version

5. Create and test a connection

The labs all take a -c <connection-name> argument. Create one interactively:

snow connection add

You will be asked for a connection name, your account identifier, user, and how you authenticate. Then test it -- do not skip this:

snow connection test -c <your-connection-name>

A working connection prints your account, user, role and warehouse. Optionally make it the default so you can drop the -c flag:

snow connection set-default <your-connection-name>

If your account requires MFA, you will be prompted on every single command, which is miserable during a workshop. Enable MFA caching so you authenticate once every four hours -- see multi-factor authentication. Alternatively use key-pair authentication.

Connections live in ~/.snowflake/config.toml on macOS and %USERPROFILE%\.snowflake\config.toml on Windows. Run snow --info to see the exact path your installation uses.

6. Verify everything, once

This step is yours to run, and it is the one we cannot do for you. Your workshop facilitator has no login in your Snowflake account, so the only way anyone finds out which labs your account supports is if you run this check and send back the output. Please do it well before the session — a few days at least, so there is time to fix anything it flags.

Every attendee should run it under their own login, not just whoever administers the account. Privileges belong to roles: a clean run as ACCOUNTADMIN says nothing about whether the role you will actually use on the day can create a database. Paste the full output back to your facilitator rather than summarising it — the detail is what determines which labs get run.

Get the workshop repository, then run the prerequisite checker. It is read-only apart from probe B5, which creates a throwaway database named after your user and drops it again immediately.

git clone <workshop-repo-url>
cd coco-interactive-workshop
snow sql -f admin_setup/00_prereqs_check.sql -c <your-connection-name>

The script has two parts:

  • Section A is one query that always succeeds. It prints your account, region, role and whether you have ACCOUNTADMIN.
  • Section B is five capability probes. Some of these are meant to fail depending on your account -- a failure is the answer, not a bug. Run them one at a time.
ProbeChecksIf it fails
B1Cortex AI functions respond Cross-region inference is probably off, or CORTEX_USER was revoked. Go back to step 2. Fix this one.
B2Live warehouse credit usageLab 14 loses its live tier and uses seeded data instead.
B3ACCOUNT_USAGE accessLab 14 cannot show what CoCo itself cost. Everything else works.
B4Enterprise Edition featuresLabs 03 and 12 use their documented fallbacks.
B5Creating and dropping a databaseNothing will run. Go back to step 1.

You are ready when Section A prints your account, probe B1 returns OK, and probe B5 succeeds. Everything else is optional and only narrows which labs you can run.

Troubleshooting

SymptomCause and fix
No CoCo in Snowsight, or it will not respond Almost always cross-region inference disabled (step 2). Otherwise a per-surface credit limit set to 0, or SNOWFLAKE.CORTEX_USER revoked from your role.
Model "..." is unavailable Cortex is reachable but that model is not available to your account or region. Enabling ANY_REGION gives the widest selection.
cortex: command not found Installed to ~/.local/bin, not on PATH. See step 3.
snow: command not found Open a new terminal after installing. If it persists, the Python tool path is not on PATH.
Prompted for MFA on every command Enable MFA caching, or switch to key-pair authentication. See step 5.
Insufficient privileges when a lab sets up Missing CREATE DATABASE. See step 1.
Invalid identifier 'INFORMATION_SCHEMA...' Only appears if you hand-write a query against a table function without a database qualifier. The lab scripts already handle it.
PowerShell blocks the install script Set the execution policy for the current process only. See step 3.

A note on the two CLIs, and on the name

Two things routinely confuse people:

  • snow is the Snowflake CLI -- it runs SQL and manages Snowflake objects. cortex is the CoCo CLI -- it is the agent. The labs use both, and they are installed separately.
  • CoCo was called Cortex Code until Snowflake Summit on 2 June 2026. Same product. Documentation URLs, the CORTEX_CODE_* account parameters and the CORTEX_CODE_*_USAGE_HISTORY views all still use the old name, so expect to see both.
